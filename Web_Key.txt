WIGLO — MASTER WEB KEY (FINAL)
===========================================

THIS IS FOR THE AI ONLY.
Goal: When asked to build an app/site, follow this spec strictly to avoid the default AI/template look.
If user requirements conflict with this key: ask or choose the more “real product” option (unless user explicitly overrides).

PRIORITY ORDER (MANDATORY)
1) Real product feel (ship-ready behavior)
2) Calm, neutral dark UI (layered greys, low saturation)
3) Clarity + usability + interaction states
4) Correctness + state wiring
5) Features (avoid feature soup)

GLOBAL ENFORCEMENT RULE
Everything in this document is REQUIRED unless it explicitly says OPTIONAL.
“MUST / DO NOT / NEVER / REQUIRED” = hard rules.
“Preferred / Avoid” = still rules (follow unless user explicitly overrides).
Do not treat non-MANDATORY sections as optional.
If any rule conflicts, follow PRIORITY ORDER and explain the tradeoff internally (do not narrate to user).


------------------------------------------------------------
0) PRIME DIRECTIVE (MANDATORY EVERY TIME)
------------------------------------------------------------
Before delivering:
A) Critic Pass: remove anything that whispers “template/AI”.
B) Functional QA: verify everything is wired and state-driven.
C) Screenshot test at 100% + 110%. If it reads template, simplify.

If you cannot visually check:
- remove glows/shadows
- reduce borders
- remove boxes/cards
- simplify layout
- remove marketing copy

------------------------------------------------------------
1) PRODUCT THINKING (ANTI “FEATURE SOUP”)
------------------------------------------------------------
1.1 One-sentence purpose
Write (internally): “This app helps X do Y.” Everything must serve that.

1.2 Page discipline
- Each page has 1 primary job.
- Each page has max 3 primary actions.
- If an element doesn’t earn its space, delete it.

1.3 Real app structure (default)
Prefer: “sidebar + list/table + details/inspector”.
Avoid: “hero + 3 cards + CTA” unless user explicitly wants a landing page.

1.4 Card quota (anti-wall rule)
- If >6 cards visible at once, you’re probably doing it wrong.
- Prefer lists/rows + spacing + headings.
- Never show a grid of equal-weight tiles without search/filter/grouping.

------------------------------------------------------------
2) INFORMATION ARCHITECTURE + LAYOUT
------------------------------------------------------------
2.1 Default skeleton
- Top bar: page title + 1 functional subtitle OR toolbar
- Main: primary content (list/table/form)
- Optional: right inspector/details panel (only if needed)

2.2 Two-column rules
- Only use 2 columns when one side is clearly secondary (details, inspector).
- If the secondary panel is empty >50% of the time: collapse/remove/redesign.

2.3 Alignment + spacing rhythm (this kills AI vibe)
- Use a spacing scale and stick to it: 4 / 8 / 12 / 16 / 24 / 32 / 48.
- If two things look like they should align, they MUST align.
- Avoid “almost aligned” edges and random padding.

2.4 Density presets (pick one per app)
COMPACT (tool-like): tighter rows, more data visible.
COMFORTABLE (default): balanced.
AIRY (marketing-ish): only if content is minimal.

------------------------------------------------------------
2.5) PRO POLISH RULES (ANTI-AI MULTIPLIERS)
------------------------------------------------------------
These are the small patterns top-tier product UIs share. Apply them by default.

A) Screen intent (must be true for every view)
- Define internally: Primary object, primary action, primary status.
- If you cannot name those 3, the layout will drift into generic template soup.

B) Domain-shaped nouns (no generic “items” UI)
- Replace “item / thing / entry” with real nouns (Track, Ticket, Note, Job, Clip, Repo, etc.).
- Buttons must be domain verbs (“Queue”, “Archive”, “Publish”, “Retry sync”, “Export CSV”).

C) Content realism (mandatory stress data)
Include data edge-cases:
- very long titles (60–120 chars), very short titles, weird characters, missing fields
- huge counts, zero counts, empty lists, “ugly” row that forces truncation/tooltip handling
- timestamps, statuses, and constraints that look plausible

D) Reduce chrome (quiet UI)
- Prefer spacing + typography over lines.
- Borders only where they clarify scroll regions or interactive containers.
- If the page looks “boxy”, remove 30–40% of containers.

E) Navigation clarity (no mystery meat)
- Active nav is unmistakable (not just slightly brighter text).
- Breadcrumbs only if hierarchy is real; do not fake them.

F) Optical alignment (looks human, not mathematical)
- Icons often need tiny vertical nudges; align by eye.
- Keep headers thin; avoid stacked thick toolbars.

G) Signature details (1–2 per project, no more)
Each project must include 1–2 subtle signature choices:
- a distinct list-row interaction
- a unique but minimal empty state layout
- a consistent custom SVG icon style (stroke weight, joins)
- a clear selection model (selected vs active vs pinned)

H) Interaction depth (minimum)
- list selection -> details/inspector
- edit mode with validation (Save disabled until changes)
- destructive action confirmation + toast with Undo when appropriate

------------------------------------------------------------
3) COLOR SYSTEM (REFERENCE PALETTES + SURFACE LADDER)
------------------------------------------------------------
Hard rules:
- No pure black (#000) backgrounds and no pure white (#fff) text by default.
- Neutrals must be slightly tinted (cool OR warm), not dead grey.
- Depth comes from surface steps + subtle overlays, not glow.

3.1 Pick ONE palette family (do not mix families)
FAMILY A — DISCORD-STYLE COOL NEUTRAL (safe default)
- bg:       #1e1f22
- sidebar:  #2b2d31
- surface:  #313338
- hover:    #383a40
- hover2:   #3d3e45
- text:     #dbdee1
- muted:    #b5bac1

FAMILY B — YOUTUBE-STYLE DEEP DARK (content-forward)
- bg:       #0f0f0f
- surface:  #181818
- surface2: #212121
- divider:  #2a2a2a (do NOT use #3d3d3d everywhere; lower it)
- text:     #ededed (not pure white)
- muted:    #aaaaaa

FAMILY C — WARM NEUTRAL (human/cozy, chess-like)
- bg:       #2c2b29
- surface:  #343231 (derive: +~6-10 brightness)
- surface2: #3c3a39 (derive)
- text:     #f0f0ee (warm off-white)
- muted:    #bcb8b0
- accent (rare): #4e7837 (and optionally lighter #69923e)

3.2 Surface ladder (mandatory in all families)
Define tokens:
- --bg
- --sidebar
- --surface
- --surface2 (headers / subtle contrast)
- --raised (menus/modals)
- --hover, --active
- --stroke (borders)
- --text, --muted, --faint
Never invent random one-off greys outside tokens.

3.3 Borders / strokes (felt, not seen)
- Use low-alpha strokes for structure.
- If a border is visible at a glance, it’s too strong.
- Prefer inset strokes on surfaces.

3.4 Elevation without glow (recommended)
Raised surfaces should be slightly lighter than base surface.
Do it by:
- using a lighter surface step OR
- compositing a subtle white overlay (very low alpha)
Avoid big drop shadows.

3.5 Accent discipline (optional)
Default: neutral-only.
If accent is needed:
- use it sparingly (underline, small indicator, link hover)
- never color-wash the whole UI
- avoid “default blue theme” vibes

------------------------------------------------------------
4) TYPOGRAPHY + ICONS (ANTI-AI / REAL PRODUCT TYPE)
------------------------------------------------------------
Goal: Avoid the “every AI website uses the same font” vibe. Typography should feel chosen, not default.

4.1 Font strategy (pick deliberately)
- Pick ONE primary UI family for the whole app.
- Optional: pick ONE display family for headings only (sparingly).
- Pick ONE mono family for code/numbers (tables, logs).
- Don’t mix 3–4 random fonts. If it feels “designed”, it’s too much.

4.2 Default behavior (safe)
- Default UI font: Inter (variable).
- If the app feels “too Inter / too AI”: switch to one of the packs below.

4.3 “Font packs” (FREE / SAFE / HUMAN-LOOKING)
Choose ONE pack per project unless user explicitly overrides.

PACK A — SYSTEM-NATIVE (most human; least “template”)
Use when: you want it to feel like a real OS app and avoid web-template vibes.
- UI stack: system-ui / -apple-system / Segoe UI / etc. (see Primer-style system stacks)
- Code: ui-monospace stack
Notes:
- Great for tools, dashboards, internal UIs.
- Best performance: no font downloads.

PACK B — DEV TOOL / ENGINEERING (VS Code-ish, sharp, utilitarian)
Use when: editor, console, project manager, power user app.
- UI: Geist (Vercel) OR IBM Plex Sans OR Source Sans 3
- Code: JetBrains Mono OR IBM Plex Mono (match the family if possible)
Notes:
- These look “designed by a product team”, not a template.

PACK C — GOOGLE/CONTENT (clean, familiar, readable)
Use when: content-heavy, media, feeds, video/music UI, search-heavy.
- UI: Roboto OR Google Sans (now available via Google Fonts)
- Code: Roboto Mono OR Google Sans Mono (if using Google Sans family)

PACK D — WARM / COZY / CHESS-LIKE (more human)
Use when: community, hobby tools, “cozy dark” apps, less corporate feel.
- UI: Atkinson Hyperlegible (accessibility-first) OR Noto Sans
- Optional display: a slightly softer display face (keep subtle)
Notes:
- Use Atkinson when readability/legibility matters. It has very distinct shapes.

PACK E — MODERN/CRAFTED (subtle personality without going “startup landing”)
Use when: you want a bit of character but still minimal.
- UI: Manrope OR Work Sans OR Space Grotesk (careful: Space Grotesk is best for headings)
- Code: JetBrains Mono / ui-monospace stack

4.4 Reference notes (what big apps do)
These are “vibes”, not strict requirements:
- Discord moved to a custom font (gg sans) across surfaces.
- YouTube uses its own custom YouTube Sans across products; Roboto is still a solid free alternative.
- GitHub’s Primer uses a system stack that includes 'Segoe UI' and 'Noto Sans' in the fallbacks.
- ChatGPT/OpenAI uses proprietary brand fonts in some contexts; DO NOT assume they are free.

4.5 Type sizing + hierarchy (minimal but real)
- Body: 14–16px (default 15px is often a sweet spot for dark UIs).
- Labels: 12–13px, 600 weight.
- Titles: 18–28px, 600–750. Avoid 900 unless brand demands it.
- Line-height: keep comfortable (1.35–1.6). Dark UIs need breathing room.
- Avoid ALL CAPS UI; if used, keep it rare and small.

4.6 Icons
- Monochrome SVG icons.
- No giant decorative icons.
- No generic “AI orb” logo inside a rounded square.
- Use one icon style set (stroke weight and corner style consistent).
- Do not mix filled + outlined icons unless deliberate and consistent.


------------------------------------------------------------
5) COMPONENT + PATTERN LIBRARY (WHAT LOOKS REAL)
------------------------------------------------------------
5.1 Navigation (sidebar)
Preferred:
- Row items (icon + label)
- Hover: subtle fill
- Active: slightly stronger fill
- Optional: compact mode (icons-only) + expand button

Sidebar behavior (modern app feel):
- Collapsible with a clear chevron/hamburger.
- Resizable via drag handle (subtle, only appears on hover near edge).
- On mobile: becomes a drawer.

BRAND AREA RULE (TOP-LEFT) (MANDATORY)
The sidebar header/brand area may contain ONLY:
- empty space, OR
- logo only, OR
- name only, OR
- logo + name
No taglines, subtitles, extra status text, version labels, or descriptive copy in that area.

5.2 Tabs / view switching
Avoid segmented pill navigation by default.
Use:
A) Underline tabs (text-only, active underline)
B) Simple list nav (chat-like)
Only use segmented controls for true mode toggles.

5.3 Buttons
Default buttons are text-like:
- transparent
- hover: subtle fill
- active: slightly stronger
Primary button only if the page has a true primary action (one per view).

BUTTON SIZING + TOOLBAR RULES (MANDATORY)
- No oversized “action tiles” for normal actions (Refresh, Add, Copy, Open).
- Default button height: 28–34px (icon buttons) / 32–36px (primary buttons).
- Default icon size in buttons: 16–20px. Never 48–96px icons in buttons.
- Toolbars must use compact controls (text button, icon button, or small split button).
- If an action must be emphasized, use position + spacing, not size (no big squares).
- If a big callout is needed, it must be an empty state CTA, not a toolbar control.


5.4 Search + inputs
- Search input: pill or soft rounded rect, dark fill, inset stroke.
- Focus: stronger inset stroke (NO glow).
- Placeholder: muted, readable.

5.5 Lists/tables (big “real app” signal)
- Rows with hover fill (minimal gridlines).
- Selected state stronger than hover.
- Secondary actions (⋯, +, trash) appear on hover OR on selection (not always visible).
- If “now playing”/active state exists, it must be distinct from selection.

5.6 Inspector / details panel (right side)
- Shows details for current selection.
- If nothing selected: show a calm placeholder + 1 action suggestion.
- Panel can be collapsed.
- If the panel is optional, keep it hidden until an item is selected.

5.7 Empty states (non-cute, functional)
- 1 line describing what’s missing
- 1 primary action (e.g., “Import…”, “Create…”)
No illustrations unless user asked.

5.8 Modals / overlays
- Never leave invisible overlays blocking clicks (see Overlay Safety).
- Modal content should feel like a real product: short, clear, “Cancel / Save”.

MODAL VIEWPORT CONSTRAINT (MANDATORY)
- Modals/drawers must fit the viewport:
  - max-height: 85vh
  - max-width: min(92vw, 960px)
- Modal body MUST scroll internally:
  - overflow: auto
- Do not use huge icons inside modals:
  - cap hero icons to ~120–180px height


5.9 Toasts / notifications
- Small, top-right or bottom-left.
- Auto-dismiss with pause-on-hover.
- Don’t over-animate.

5.10 Command palette (only if app benefits)
- Ctrl+K or / to open.
- Must not trigger while typing in inputs.
- If present, document in Settings → Shortcuts.

------------------------------------------------------------
6) MOTION / ANIMATION (OPTIONAL BUT CAN MAKE IT FEEL HUMAN)
------------------------------------------------------------
Default: minimal. Motion must communicate state or spatial change.

Hard rules:
- Respect prefers-reduced-motion (reduce/disable transitions).
- No bouncy springs everywhere.
- Animate only transform/opacity where possible (performance).
- Direction must be consistent: open direction = close direction.
- At least one spatial transition MUST exist if the UI has panels/drawers/modals (drawer slide or modal fade)

6.1 Timing presets
- Micro (hover/focus): 120–180ms ease-out
- Small UI changes (expand/collapse sections): 160–220ms
- Panels/drawers (slide in/out): 180–260ms
- Modals (fade + slight scale): 160–220ms

6.2 “YouTube comment panel” style pattern (recommended)
Use for: inspector, comments, activity log, notifications.
Behavior:
- Panel slides in from right
- Scrim appears subtly
- Content fades in slightly after panel starts moving
- Close reverses exactly (same direction)

6.3 Sidebar collapse/expand motion
- Collapse: width shrinks + labels fade out
- Expand: width grows + labels fade in after movement starts

6.4 Reduced motion handling
If prefers-reduced-motion:
- remove sliding; use instant show/hide or quick fade only.

------------------------------------------------------------
7) ENGINEERING (MAKE IT WORK LIKE A REAL APP)
------------------------------------------------------------
7.1 Project structure (default static)
- /css/app.css
- /js/app.js
Optional split:
- /js/state.js (single source of truth)
- /js/ui.js (render + event binding)
- /js/data.js (loading/parsing)

7.2 State architecture (mandatory)
Single source of truth for:
- selectedId
- activeView
- search/filter/sort
- sidebarCollapsed + sidebarWidth
- panelOpen + panelWidth
- any “active” concept (nowPlaying, currentItem, etc)

UI derives from state. Never “last click” UI.

7.3 Persistence
If it improves UX:
- localStorage for UI state (collapsed, widths, last view)
- On load: hydrate -> render -> sync highlights

7.4 Event rules
- Bind events once.
- Prefer delegation for list rows.
- Handlers update state -> render minimal areas.
- After mutations: save() then render().

7.5 Performance rules
- No heavy blur, no giant shadows.
- Virtualize long lists if needed.
- Avoid 500-line functions and fake abstractions.

7.6 OVERLAY SAFETY INVARIANT (MANDATORY)
Any full-screen overlay container (modal host, toast host, command palette) using:
  position: fixed; inset: 0;
MUST be non-interactive when closed.
Never rely on opacity alone.
Use [hidden]{display:none} OR pointer-events:none in closed state.

7.7 SCROLL CONTAINMENT (MANDATORY)
- The page background (body) should not be the primary scroller in app-like layouts.
- Use a fixed app shell: header + main area, and make only the main content panes scroll.
- Sidebar, main content, and inspector panels should scroll independently when needed.
- Modals/drawers scroll internally (never exceed viewport).
- Avoid scroll chaining surprises: don’t trap the user; just keep scroll regions predictable.

------------------------------------------------------------
8) ACCESSIBILITY + UX SANITY
------------------------------------------------------------
Minimum:
- Keyboard focus styles (visible, not glowing).
- Proper semantics (button tags, labels, aria where needed).
- Contrast sanity (muted text still readable).
- Click targets not tiny.
- Hover isn’t the only discovery: show actions on selection too.

------------------------------------------------------------
9) MICROCOPY (ANTI-TEMPLATE LANGUAGE)
------------------------------------------------------------
Tone: short, functional, calm.
Prefer: “Import”, “Export”, “New…”, “Remove”, “Retry”.

Hard ban phrases (default):
- design-first, curated, modern layout, elevate, seamless, next-gen, premium, intuitive, powerful

Rules:
- No “marketing rhythm” everywhere.
- Slightly uneven sentence length is fine.
- Don’t narrate the UI (“This page helps you…”) except onboarding/empty states.

------------------------------------------------------------
10) RESPONSIVE (NO DESKTOP-ONLY DASHBOARD)
------------------------------------------------------------
Breakpoints:
- Desktop >= 1100px
- Tablet 800–1099px
- Mobile < 800px

Behavior:
- Sidebar becomes drawer on mobile.
- Two-column stacks (details below list).
- Keep actions reachable (toolbar sticks or moves smartly).

------------------------------------------------------------
11) DELIVERY STANDARD (ANTI-PROTOTYPE)
------------------------------------------------------------
SHIP MODE (MANDATORY)
- The delivered UI must look like a ready public product, not a dev demo.
- Do NOT include developer-only UI in the product surface:
  - no “Tools / Diagnostics / Self-Test / Simulate error/loading” buttons
  - no debug panels, no placeholder dev notes, no “press / to search” hints unless it’s truly a user feature
- Dev/testing utilities (if they exist at all) must be removed or hidden behind a non-obvious dev flag and MUST be off by default.
- README may include setup/customize notes, but the app UI must not expose dev/testing controls to normal users.
- No dead code, no placeholder “demo” copy.
- Set real <title>, favicon, and consistent naming.
- README: how to run locally, what data lives where, limitations (honest).
-QA utilities may exist only behind ?dev=1 (or similar) and MUST be off by default.

------------------------------------------------------------
12) CRITIC + QA PASSES (NO EXCEPTIONS)
------------------------------------------------------------
PASS A — Visual Critic
- Any glow? remove.
- Borders too strong? reduce/remove.
- Too many boxes/cards? remove 30–40%.
- Symmetry/template blocks? break them.
- Generic copy? rewrite.

AI-TELL QUICK TEST (run last)
- If you can describe the page as “dashboard-ish”, it’s too generic -> make it more domain-shaped.
- If it’s a grid of equal cards -> convert to list + inspector.
- If accent appears in >3 places in one viewport -> reduce it.
- If too many buttons look equally important -> demote most to text buttons.
- If microcopy has any buzzwords -> rewrite to functional domain language.

PASS B — Layout
- Alignment clean.
- Spacing scale consistent.
- No giant empty panels.
- Search/toolbar aligned to content grid.

PASS C — Interaction
- Hover/active/focus consistent.
- Selected vs “active/now playing” distinct.
- Sidebar collapse and panel slide behave correctly.

PASS D — Functional QA (“Dead UI” smoke test)
On EACH page:
- Click nav
- Use primary action
- Use search
- Open/close any drawers/modals
- Refresh (state still consistent)

If any click doesn’t register: suspect overlays/z-index/pointer-events first.

APPENDIX: BACKEND KEY (ONLY IF SERVER IS USED)
============================================================
B1) Avoid backend “AI smells”
- microservices/over-architecture
- fake enterprise boilerplate
- auth/JWT “just because”
- unused dependencies
- vague “Something went wrong” everywhere

B2) Preferred backend vibe
- small, boring, correct
- minimal files, clear naming

------------------------------------------------------------
14) ASSETS (ICONS/LOGOS/IMAGES) (PREFERRED ORDER)
------------------------------------------------------------
Preferred order:
1) Generate simple vector assets yourself (SVG): app mark/logo, icons, tiny illustrations.
2) Use free external images ONLY if needed and only if they are clearly licensed for reuse (e.g., Unsplash/Pexels) and you include attribution in README when required by the license.
3) Never hotlink random images from Google results.

Rules:
- Keep assets minimal, monochrome or low-saturation, consistent with the UI.
- Avoid generic “AI orb” logos.
- Prefer SVG for crispness; embed inline or store in /assets (if using /assets, include it in the ZIP).
- External images must be downloaded into the project (no external URLs at runtime) unless the user explicitly allows hotlinking.

APPENDIX A) WHAT PEOPLE CALL “AI WEBSITE LOOK” (COMMUNITY SIGNALS)
---------------------------------------------------------
(Condensed from webdev/Reddit discussions where people say a site “looks AI-made”.)

A1) Template-ish composition
- Centered “hero + 3 feature cards + testimonials + pricing” even when the product is not SaaS.
- Too-symmetrical grid, everything perfectly aligned and evenly spaced like a template.
- Over-structured sections: many containers, many borders, many cards, no breathing negative space.

A2) Generic design tokens / “Tailwind default vibe”
- Default shadcn/tailwind UI look (typical button shapes, typical cards, default radii, default shadow).
- The same radius everywhere, same stroke everywhere, same spacing everywhere.
- “Design system” feels copied rather than built for the product.

A3) Color tells (especially in dark mode)
- The “random purple” or “blue-purple gradient” that screams AI/crypto/SaaS.
- Too-bright accent, too much saturation on dark backgrounds.
- Glow everywhere (drop shadows, neon focus rings, soft bloom behind sections).

A4) Typography tells
- Overly polite, marketing-y copy. Generic microcopy like “Get started”, “Boost productivity”, “Seamless”.
- Too many emojis, too many “friendly” headlines, too much hype.
- Headings are too similar in size/weight; no real hierarchy.
- Monotone line-height and spacing (robotic).

A5) Interaction tells
- Hover effects are dramatic (scale-up cards, big shadow, big color shift).
- Animations are either absent (lifeless) OR excessive and “demo-y”.
- No real “product behaviors” (empty states, error states, keyboard navigation, loading skeletons).

A6) Content tells
- Fake metrics, fake logos, generic testimonials.
- Placeholder data that feels random/unrealistic (“Project A”, “John Doe”, “Acme Inc.”).
- No constraints: never shows “long titles”, “no results”, “permission denied”, “offline”.

A7) How to counter it (rules you should add as hard QA items)
- Every page MUST have at least:
  - a real empty state
  - a real loading state (skeleton or spinner used sparingly)
  - a real error state
  - a realistic data stress test (long names, huge lists, slow network)
- Prefer product-shaped layouts (tool UI) over marketing landing pages unless explicitly asked.
- Use a “boring real app” color model: neutral surfaces + subtle strokes + restrained accent.

APPENDIX C) SURFACE ELEVATION WITHOUT “SHADOW GLOW” (DARK MODE OVERLAY TABLE)
--------------------------------------------------------------------
Problem:
- Dark UIs look fake when you add lots of drop shadows.
Solution:
- Use “overlay elevation” (slightly lighter surface) instead of “floating shadow”.

Material-style approach (base #121212 + white overlay).
(Source: StackOverflow community mapping based on Material dark theme guidance.)

Elevation overlay mapping:
00dp | overlay 0%  | #121212
01dp | overlay 5%  | #1e1e1e
02dp | overlay 7%  | #222222
03dp | overlay 8%  | #242424
04dp | overlay 9%  | #272727
06dp | overlay 11% | #2c2c2c
08dp | overlay 12% | #2e2e2e
12dp | overlay 14% | #333333
16dp | overlay 15% | #343434
24dp | overlay 16% | #383838

How to use it in web UI:
- Base background: 00dp
- Cards/panels: 01–04dp (subtle)
- Modals/popovers: 06–12dp (still subtle)
- Avoid “24dp everywhere”. If you need 24dp, you probably need less UI density.

APPENDIX D) PROFESSIONAL “TOOL UI” LAYOUT PATTERNS (VERY HUMAN, VERY COMMON)
--------------------------------------------------------------------
D1) 3-layer app shell (super common)
- Left: primary nav rail / workspace list (collapsible)
- Middle: main content (list/table/editor)
- Right: details inspector (optional, collapsible, slides in)
This is used everywhere because it scales: GitHub, Discord, VSCode, Figma-ish tools.

D2) Collapsible sidebar with “arrow” affordance (do this)
- Provide a clear “collapse” icon at the bottom or top of sidebar.
- Collapsed state becomes icon-only rail (56–72px).
- Remember state (localStorage).
- Don’t animate too long: 180–260ms.

D3) Resizable split panes (do this when you have list + detail)
- List pane default ~320–420px.
- Drag handle 6–10px wide (invisible but usable); cursor: col-resize.
- On drag: show a 1px guide line, not a huge overlay.
- Save the width after drag ends.

D4) Inspector panels (right side) with slide-in
- Use when selecting an item reveals details.
- Closed by default on mobile.
- Slide-in from right; keep “scrim” minimal or none in desktop tool UIs.
- If there is a scrim: very subtle (black at 0.25–0.35).

D5) Sticky headers (but not thick)
- A thin sticky bar for search/filter/sort.
- Keep it one row, not multiple stacked toolbars.
- Prefer “one good search” + “one filter dropdown” over 12 chips.

D6) “Command palette” for power actions
- Ctrl+K or / opens it.
- It reduces UI clutter (no need to show every action as a button).
- If present, it must not look like a template: keep it plain, tight, and fast.

D7) Lists feel human when they have:
- row hover
- selection
- keyboard nav (↑↓, Enter)
- context menu (right click / ... menu)
- empty states
- subtle separators (or none, using spacing)
APPENDIX E) MOTION + MICROINTERACTIONS (HUMAN, NOT DEMO-Y)
--------------------------------------------------
General:
- Motion should communicate state changes and spatial relationships.
- Motion must be consistent across the app.
- Use transform + opacity, not box-shadow growth.
- Respect prefers-reduced-motion.

E1) Timing defaults (safe)
- micro hover/focus: 120–160ms
- simple expand/collapse: 160–220ms
- panel slide in/out: 220–280ms
- modal popover: 160–220ms
- list reorder/insert: 160–220ms

E2) Easing defaults (safe)
- ease-out for entrances (fast start -> soft stop):
  cubic-bezier(0.16, 1, 0.3, 1)
- ease-in for exits (soft start -> faster finish):
  cubic-bezier(0.7, 0, 0.84, 0)
- avoid “bouncy spring” unless it’s a playful app.

E3) Panel slide recipe (YouTube comments style)
- Start: x=24px, opacity=0
- End: x=0px, opacity=1
- Duration: 220–260ms
- Easing: ease-out (above)

CSS:
.panel{
  transform:translateX(24px);
  opacity:0;
  transition:transform 240ms cubic-bezier(.16,1,.3,1), opacity 180ms ease-out;
}
.panel[data-open="true"]{
  transform:translateX(0);
  opacity:1;
}

E4) Dropdown / popover recipe
- Start: y=-4px, opacity=0, scale=0.98
- End: y=0, opacity=1, scale=1
- Duration: 140–180ms
- Easing: same ease-out

E5) “Slightly alive” without looking like AI demo
- Subtle skeleton shimmer (slow, low contrast) OR static skeleton.
- One tasteful animation per screen max (don’t animate everything).

E6) Reduced motion
- If prefers-reduced-motion: disable transform animations, use opacity only (fast).
APPENDIX F) “REAL PRODUCT” DETAILS THAT BREAK THE AI TEMPLATE FEEL
---------------------------------------------------------
These are the tiny things humans subconsciously expect.

F1) Stress test content (do it before shipping)
- Very long names (60–120 chars)
- Empty lists
- Large lists (100–1,000 rows)
- Failed network request
- “No permission”
- Offline mode (optional)
- Slow response (spinner or skeleton)

F2) Real empty states (not marketing)
Bad: “No items yet. Start by creating your first amazing item!”
Good: “No projects.” + a short reason + one clear action button.
Even better: “No projects” + “Import” option + “Create new”.

F3) Real error states
- Show what happened in normal language.
- Provide one recovery action.
- Provide “Copy error details” in advanced section.

F4) Real microcopy tone (tool UI tone)
- Short, calm, direct.
- Avoid hype words: “seamless”, “revolutionary”, “empower”, “unlock”.
- Avoid emoji unless the app is actually playful.

F5) Keyboard affordances
- Tooltips show shortcut hints (Ctrl+K).
- Inputs respect Enter/Esc.
- Modal: Esc closes, focus trap works.

F6) Scroll behavior
- Long panes scroll independently (sidebar scroll separate from main).
- Sticky headers don’t stack.

F7) Context actions
- Item rows have a subtle “…” menu on hover.
- Right-click opens context menu (desktop).

F8) “This was made by a human” detail
- One or two opinionated choices:
  - slightly unusual spacing in one area
  - a custom empty-state illustration (minimal)
  - a custom icon (not generic AI logo)
APPENDIX G) SNIPPET RECIPES (FOR IMPLEMENTATION CONSISTENCY)
---------------------------------------------------
These are “known good” patterns that keep you out of template hell.

G1) Token-first CSS (do this)
- Put tokens in :root (or CSS variables in Tailwind config).
- All components must reference tokens, not raw colors.

G2) Low-contrast strokes (rule)
- Prefer alpha strokes over solid hex.
Examples:
- rgba(255,255,255,0.06) for subtle dividers on dark
- rgba(255,255,255,0.10) for focused outlines
- Avoid pure #333 borders everywhere.

G3) Resizable split pane (vanilla JS)
HTML:
<div class="split">
  <aside id="left"></aside>
  <div id="gutter" aria-hidden="true"></div>
  <main id="main"></main>
</div>

CSS:
.split{display:grid;grid-template-columns:320px 8px 1fr;height:100%;}
#gutter{cursor:col-resize;background:transparent;position:relative;}
#gutter::after{content:"";position:absolute;left:3px;top:0;bottom:0;width:1px;background:rgba(255,255,255,.06);opacity:0;transition:opacity 120ms;}
#gutter:hover::after{opacity:1;}

JS:
const left=document.getElementById("left");
const gutter=document.getElementById("gutter");
let dragging=false,startX=0,startW=0;
gutter.addEventListener("pointerdown",(e)=>{
  dragging=true;startX=e.clientX;startW=left.getBoundingClientRect().width;
  gutter.setPointerCapture(e.pointerId);
  document.body.style.cursor="col-resize";
});
gutter.addEventListener("pointermove",(e)=>{
  if(!dragging) return;
  const w=Math.max(220,Math.min(520,startW+(e.clientX-startX)));
  document.querySelector(".split").style.gridTemplateColumns=`${w}px 8px 1fr`;
});
gutter.addEventListener("pointerup",(e)=>{
  dragging=false;document.body.style.cursor="";
});

G4) Sidebar collapse (layout safe)
- Keep DOM stable; just change grid column widths.
- Animate width change (but not too slow).
- Save state to localStorage.

G5) Focus ring (non-glowy)
- Use outline: 2px solid rgba(accent, .55) with 1px offset.
- No outer shadow halo.

G6) Shadow policy (dark mode)
- Avoid big drop shadows. Use:
  - inset stroke
  - surface elevation (overlay table)
  - very small shadow only for popovers if needed:
    0 8px 24px rgba(0,0,0,.35) (single layer, no glow)
APPENDIX H) OPTIONAL: “PALETTE EXTRACTION” METHOD (IF YOU WANT MORE APP MATCHING)
------------------------------------------------------------------------
If you want to match a specific website/app:
- Open DevTools → Inspect the sidebar background, main background, input background, stroke color, and text color.
- Record them as tokens:
  --bg0, --bg1, --surface0, --surface1, --stroke, --text, --muted, --accent
- Then build the rest (hover fills, selection fills) using alpha of text or muted text.

Rule of thumb for hover/selection on dark:
- hover fill: text color at 6–10% alpha
- selection fill: text color at 14–22% alpha
- pressed: selection + a bit darker (or 26% alpha)
